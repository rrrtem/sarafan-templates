# Спецификация: HTML-шаблоны SMM и MCP-сервер на Vercel

Дата: 22 октября 2026 года. Версия документа: 1.0.
Статус: подготовлено для проверки владельцем; реализация не начата.
Рабочее название: SARAFAN SMM Kit.

## 1. Цель и ожидаемый результат

Создать переносимую библиотеку дизайн-системы и шаблонов для SMM. Владелец пишет задание в ChatGPT, Claude или другом совместимом MCP-клиенте, агент получает материалы проекта, создаёт пост и возвращает превью и оригинальный PNG. Компьютер владельца может быть выключен. Открывать отдельный сайт для ежедневной работы не требуется.

Два обязательных сценария:

1. Создать пост по существующему шаблону, заменяя содержание и выбирая разрешённые варианты.
2. Создать новую композицию в рамках той же дизайн-системы, сохранить её и повторно использовать.

Независимость от модели означает общие файлы, JSON Schema и MCP-инструменты. Система не требует определённой модели, её API-ключа, фирменного формата skill или собственного LLM-агента на сервере. MCP-клиент должен уметь подключаться к удалённому серверу и вызывать инструменты; совместимость с любым произвольным чатом не предполагается.

## 2. Принятый подход и рассмотренные варианты

| Вариант | Преимущества | Ограничения | Решение |
| --- | --- | --- | --- |
| Vercel: MCP, Chromium и Blob | Одна платформа для выполнения и хранения; не нужен собственный интерфейс | Нужны настройка браузера, авторизация и учёт ресурсов | Выбран для первой версии |
| Vercel и Supabase | Удобная база для команды, сложной истории и поиска | Дополнительный сервис и модель данных | Отложен до появления таких требований |
| Локальный проект с рендером на компьютере | Простой запуск и полный контроль среды | Удалённая работа зависит от доступности компьютера | Допускается для разработки, не является рабочей инфраструктурой |

Все серверные компоненты первой версии размещаются на Vercel. Исходники хранятся в обычном Git-репозитории. Supabase, Redis, внешний браузерный сервис и LLM API не являются обязательными зависимостями.

## 3. Границы первой версии

### Входит

- Один владелец и один бренд на развёртывание, несколько его MCP-клиентов.
- Общая дизайн-система, утверждённые шаблоны и примеры.
- Отдельные карточки и карусели до 10 карточек.
- Создание, повторный рендер и сохранение версий.
- Новые композиции из разрешённых элементов.
- PNG в полном размере, компактное превью, JSON содержания и HTML-снимок результата.
- Доступ с телефона через удалённый MCP.
- Приватное файловое хранилище, авторизация и ограничение рендеров.

### Не входит

- Собственная чат-платформа, редактор макетов и сайт-галерея.
- Команды, роли сотрудников, несколько брендов и биллинг пользователей.
- Публикация в соцсети, контент-план и аналитика охватов.
- Генерация фото или иллюстраций, видео, анимация и SVG как итоговый формат поста.
- Произвольный JavaScript, запуск кода агента и выполнение присланных HTML-страниц.
- Изменение дизайн-системы, Git-репозитория или деплой через MCP.
- Фоновая автономная генерация после завершения вызова инструмента.
- Гарантия бесплатной коммерческой эксплуатации.

## 4. Сценарии владельца

### 4.1. Пост по шаблону

Владелец просит: «Сделай анонс новой коллекции по шаблону с большой фотографией». Агент читает правила и каталог, получает описание выбранного шаблона, создаёт пост и передаёт содержание на рендер. Сервер проверяет ограничения и возвращает результат или конкретные ошибки. Агент исправляет содержание и повторяет запрос при необходимости.

### 4.2. Правки

Владелец просит заменить заголовок или фотографию. Агент получает сохранённый пост, создаёт новую версию нужной карточки и возвращает новое изображение. Предыдущая версия сохраняется; остальные карточки не меняются.

### 4.3. Новая композиция

Агент собирает новое расположение разрешённых блоков. Сервер компилирует его в HTML, проверяет и рендерит. Новая композиция сохраняется как черновик и может использоваться повторно по идентификатору. Статус черновика не означает, что визуальное решение одобрено владельцем.

Перевод черновика в утверждённую библиотеку выполняется отдельным изменением исходников после согласования владельцем. В первой версии MCP не публикует шаблоны и не меняет базовые правила. Это редкая операция сопровождения, а не обязательное действие при создании каждого поста.

### 4.4. Карусель и прерывание чата

Агент создаёт пост с числом карточек, затем рендерит их последовательно, по одной за вызов. Владелец видит готовые карточки по мере выполнения. После прерывания чата уже сохранённые результаты доступны через `get_post`; агент может продолжить недостающие карточки. Незавершённая работа сама по себе в фоне не продолжается.

## 5. Архитектура и границы модулей

| Модуль | Ответственность | Зависимости |
| --- | --- | --- |
| Brand package | Правила, токены, разрешённые блоки, шаблоны и примеры | Стандартные файлы Markdown, JSON, HTML, CSS и локальные ресурсы |
| Layout compiler | Проверка входных данных и преобразование разрешённой композиции в статический HTML/CSS | Brand package и JSON Schema; без Vercel SDK и LLM SDK |
| Renderer | Chromium, загрузка ресурсов, проверки геометрии, PNG и превью | Скомпилированный документ и локальные ресурсы |
| Repository adapter | Чтение и запись постов, версий, ресурсов и состояния операций | Vercel Blob; изолированный интерфейс для замены хранилища |
| MCP adapter | Инструменты, схемы, описания и ответы клиентам | Прикладные операции; не содержит правил дизайна |
| Access module | Вход владельца, OAuth и проверка доступа | Серверные маршруты того же приложения; служебное состояние в приватном Blob |

MCP работает по HTTPS и Streamable HTTP через `/api/mcp`. Используется Node.js runtime. Сервер остаётся работоспособным при холодном запуске: существенное состояние не хранится только в памяти процесса.

Для Vercel используется Puppeteer Core и совместимая serverless-сборка Chromium. Версии браузера, Node.js, библиотек и шрифтов фиксируются. Рендер запускается после установки явного размера холста, загрузки шрифтов и декодирования изображений.

HTML и браузерный контекст не получают Blob-токены, OAuth-секреты или переменные окружения серверной функции. Изображения и шрифты поступают в документ через контролируемый резолвер ресурсов.

## 6. Дизайн-система и источник истины

Дизайн-система состоит из:

- `rules.md`: композиция, иерархия, работа с текстом и фото, разрешённые исключения.
- `tokens.json`: единственный источник значений цветов, типографики, интервалов, размеров и других параметров. Формат совместим с DTCG.
- Общих стилей, получаемых из токенов, без ручной синхронизации дубликатов значений.
- Схем разрешённых компонентов и свойств.
- Профилей холста и безопасных зон.
- Утверждённых визуальных примеров и коротких пояснений, почему они работают.
- Отдельных примеров нарушений с объяснением ошибки.

В правилах обязательны: семейства и начертания шрифтов, типографические роли, межстрочные интервалы, число строк, допустимые сочетания цветов, сетка, поля, интервалы, положение и минимальный размер логотипа, правила обрезки фото и поведение при нехватке места.

Текст хранится как обычный текст. HTML и произвольные CSS из текстовых полей экранируются. Фиксированные размеры и координаты разрешены только там, где их явно допускает схема компонента; произвольные значения не обходят токены.

При переполнении сервер возвращает ошибку. Агент может предложить сокращение текста, другой шаблон или дополнительную карточку. Сервер не обрезает текст и не уменьшает шрифт молча.

Каждый пакет имеет `design_system_version`, каждый шаблон — `template_version`. Пост сохраняет обе версии, исходные данные, композицию, идентификаторы ресурсов, скомпилированный HTML и контрольные суммы. Смена текущей дизайн-системы не меняет старые PNG. Повторное использование старого макета с новой системой является явной миграцией, а не скрытым обновлением.

### Наполнение бренда

Эта спецификация определяет устройство системы, но не придумывает реальные цвета, шрифты и визуальный стиль бренда. До приёмки брендовой библиотеки владелец предоставляет или утверждает логотип, шрифты, палитру и примеры постов. Тестовый набор для проверки инфраструктуры явно помечается как демонстрационный и не выдаётся за утверждённый дизайн бренда.

Первый брендовый набор должен содержать не менее трёх утверждённых шаблонов: текстовый анонс, карточку с фотографией и карточку содержания карусели. Их конкретный вид определяется на этапе наполнения дизайн-системы.

## 7. HTML и новые макеты

Экспортируемый результат каждой композиции — статический HTML/CSS и PNG. Для строгой проверки новые макеты задаются JSON-деревом разрешённых компонентов, а HTML создаётся общим компилятором. Владелец не обязан писать или видеть это дерево: его готовит агент.

Один и тот же формат композиции используется для штатных шаблонов и черновиков. Структурные блоки: canvas, stack, row, grid, box, text, image и logo. Декоративные элементы доступны только как перечисленные варианты компонента. Типы и свойства описываются JSON Schema: ссылки на токены, варианты выравнивания, допустимые колонки, области и ограничения размеров.

Агент может менять содержание, выбирать разрешённые варианты и собирать новые композиции. Он не может добавлять новый шрифт, цвет, произвольный CSS, скрипт, iframe или внешний сетевой запрос. Новый вид компонента требует изменения пакета дизайна.

Это сознательная граница первой версии: свободная композиция поддерживается внутри описанного визуального языка. Режим произвольного присланного HTML с частичной проверкой не включается, поскольку он ослабляет контроль и изоляцию.

Готовые HTML-шаблоны из других источников переносятся в общий формат при наполнении библиотеки. HTML-снимок результата самодостаточен: общие стили, фактически используемые изображения и шрифты встраиваются в него, без временных ссылок и исполняемых скриптов. Такой файл можно просматривать без MCP-клиента. Чистый компилятор и пакет бренда можно использовать на другом хостинге.

## 8. Контракт MCP

Все операции возвращают структурированные данные и короткое текстовое описание. Правила доступны через tool-вызов, поэтому работа не зависит от поддержки MCP Resources или Prompts конкретным клиентом. Read-only инструменты помечаются соответствующими аннотациями, операции записи — как изменяющие данные. Аннотации не заменяют авторизацию.

| Инструмент | Вход и назначение | Основной результат |
| --- | --- | --- |
| `get_design_system` | Получить правила, токены, схемы блоков и примеры; необязательная версия пакета | Пакет инструкций, доступные холсты и ограничения |
| `list_templates` | Фильтр по типу, холсту и статусу approved/draft; курсор; до 20 элементов | Каталог с назначением, ограничениями, версиями и ссылками на превью |
| `get_template` | Идентификатор и версия шаблона либо черновика | Схема содержания, композиция, примеры и разрешённые варианты |
| `create_post` | Название, холст, число карточек 1–10, `request_id` | `post_id`, метаданные и пустые позиции карточек |
| `render_slide` | Пост, индекс карточки, базовая версия, источник композиции, содержание, версия дизайна, `request_id` | Версия карточки, результат проверок, превью и ссылки на файлы |
| `get_post` | `post_id`, необязательный выбор версий | Содержание, состояние всех карточек, история и свежие ссылки |
| `save_layout_draft` | Композиция, описание, версия дизайна, `request_id` | Версионированный черновик для дальнейшего использования |
| `import_asset` | Прямой HTTPS URL фотографии либо небольшое base64-вложение с метаданными; `request_id` | Приватный `asset_id`, фактический формат, размер и превью |

`render_slide` принимает ровно один источник: утверждённый шаблон, сохранённый черновик или новое дерево композиции. Несовместимая версия возвращает ошибку. Индексы карточек начинаются с 1. Первая версия передаёт пустой `base_revision_id`; правка обязана ссылаться на актуальную версию карточки.

Ответ рендера включает `post_id`, `slide_index`, `revision_id`, `design_system_version`, версию шаблона при её наличии, статус проверок, компактный image-блок, ссылки на PNG, JSON и HTML, `expires_at`, размеры и контрольную сумму результата. Оригинальный PNG не передаётся большим base64-блоком внутри MCP.

В одном ответе встраивается не более одного превью. Каталог и примеры дизайн-системы используют ссылки и пагинацию, соблюдая общий лимит ответа. Запрос недоступной старой версии возвращает `VERSION_MISMATCH`; существующие HTML-снимки и PNG при этом остаются доступны.

При отказе проверок инструмент возвращает `isError`, код, список нарушений с путями к компонентам, допустимые значения и `retryable`. Исправимая ошибка не выдаётся за готовый пост. Диагностическое превью, если оно создано, помечается как не прошедшее проверки.

Прямые URL файлов, приложенных к чату, могут быть недоступны серверу. Это не считается автоматически поддержанным способом загрузки. Обязательный путь первой версии — предварительно размещённые в пакете изображения, доступная прямая HTTPS-ссылка или небольшое вложение, которое клиент способен передать инструменту. Загрузка большого файла непосредственно из мобильного чата проверяется отдельно для каждого клиента и не входит в гарантии протокола.

## 9. Рендер и проверки

Стартовые профили холста: 1080×1080, 1080×1350 и 1080×1920 пикселей, device scale factor 1. Это размеры файлов приложения, а не обещание актуальных требований конкретной соцсети. Профили могут сужаться правилами бренда.

Порядок выполнения:

1. Проверить доступ, лимиты, схему, версии, ссылки на ресурсы и состояние карточки.
2. Получить блокировку рендера и зафиксировать идентификатор попытки.
3. Скомпилировать композицию в статический документ с общими стилями.
4. Открыть изолированный браузерный контекст; дождаться шрифтов и изображений.
5. Проверить вычисленные стили, геометрию и ограничения содержания.
6. Сохранить PNG и превью; записать неизменяемые данные версии.
7. Условно обновить манифест поста и зафиксировать успешный результат операции.
8. Закрыть браузер и освободить блокировку, включая ветку ошибки.

Обязательные машинные проверки:

- Известные токены и компоненты, допустимые значения их свойств.
- Разрешённые гарнитуры, начертания, размеры и цвета.
- Точное соответствие холсту; отсутствие неразрешённого выхода за границы и обрезанного текста.
- Число строк, необходимые поля, безопасные зоны и ограничения логотипа.
- Успешная загрузка изображений и шрифтов; отсутствие подмены недостающего шрифта.
- Отсутствие неразрешённого сетевого доступа и исполняемого содержания.

Пересечения слоёв разрешаются только для явно описанных сочетаний компонентов. Проверка не запрещает намеренное наложение текста на фото, если шаблон и правила это допускают.

Измеримые правила являются обязательными. Соответствие визуальному характеру бренда и качество новой композиции оцениваются владельцем; наличие успешного валидатора не означает художественного одобрения.

## 10. Хранение, версии и восстановление

Используется приватный Vercel Blob. Основные группы данных:

- `projects/<project_id>/posts/<post_id>/manifest.json` — текущие позиции карточек и ссылки на версии.
- `projects/<project_id>/posts/<post_id>/slides/<index>/<revision_id>/` — неизменяемые PNG, превью, HTML и JSON версии.
- `projects/<project_id>/drafts/<draft_id>/<version>/` — черновики композиций.
- `projects/<project_id>/assets/<asset_id>/` — нормализованные изображения и метаданные.
- `internal/operations/`, `internal/leases/`, `internal/auth/` — служебные записи без доступа через пользовательские инструменты.

Пути строит сервер из проверенных идентификаторов; пользователь не передаёт произвольный путь Blob. Входящий URL не подменяет `asset_id` в рендере.

Для файлов версий запрещено перезаписывать существующее содержимое. Для манифестов, блокировок и состояния OAuth используются согласованные чтения приватного хранилища и условные записи по ETag. Обычный CDN-кеш не используется для принятия решений о текущей версии, доступе или блокировках. Возможности consistent reads и conditional writes Vercel Blob являются обязательным условием выбранного адаптера.

Каждая изменяющая операция содержит уникальный `request_id` и хеш нормализованного ввода. Повтор с тем же идентификатором и тем же вводом возвращает прежний результат или состояние попытки. Другой ввод под тем же идентификатором возвращает `IDEMPOTENCY_CONFLICT`.

В первой версии одновременно выполняется один рендер на проект. Блокировка имеет владельца и срок действия; её получение и освобождение выполняются условно. Поздно завершившаяся попытка не может перезаписать результат нового владельца блокировки. Перед коммитом версии повторно проверяются владение попыткой и базовая версия карточки.

Сначала записываются полные файлы новой версии, затем её манифест, затем ссылка в посте. Если запись прервалась, предыдущая версия остаётся доступна. Попытка, чей срок истёк без завершения, показывается как прерванная, а не бесконечно выполняющаяся. Повтор проверяет уже подготовленные файлы и восстанавливает коммит, если это возможно, без повторного рендера.

Готовность карусели определяется наличием текущей прошедшей проверки версии в каждой заявленной позиции. Частично готовый пост возвращает готовые и недостающие позиции явно.

Оригиналы выдаются временными signed URL на чтение из приватного Blob. Срок действия по умолчанию — 1 час; `get_post` выдаёт свежие ссылки. Секреты хранилища не передаются клиентам. Ссылки только на чтение не дают права перечислять, менять или удалять объекты. HTML выдаётся как скачиваемый файл, а не исполняется в интерфейсе MCP.

## 11. Авторизация и минимальный интерфейс

Рабочий MCP закрыт OAuth 2.1 Authorization Code + PKCE S256. Авторизационный сервер и страница входа владельца находятся в том же Vercel-приложении. Для протокольной части используется поддерживаемая библиотека; собственные криптографические протоколы не создаются.

Единственный локальный владелец задаётся конфигурацией. Его пароль проверяется по стойкому salted-хешу в защищённых переменных окружения. Открытой регистрации пользователей и восстановления пароля через почту в первой версии нет; смена пароля выполняется через конфигурацию развёртывания. Страница входа и согласия открывается при подключении клиента или повторной авторизации, а не при каждом посте.

Обязательны discovery metadata, точная проверка redirect URI, привязка токена к ресурсу, проверка issuer, audience, expiry и scope. Для клиентов поддерживается стандартная dynamic client registration; выдача клиентского идентификатора не предоставляет доступ к проекту без входа и согласия владельца. Вход ограничивается платформенными правилами частоты запросов и защитой от перебора.

Минимальные scopes: `design:read`, `posts:read`, `posts:write`, `assets:write` и `drafts:write`. Инструмент проверяет требуемый scope до обращения к ресурсам; отдельного scope на изменение базового дизайна не существует.

Authorization code живёт 5 минут и погашается однократно через атомарное изменение записи. Access token живёт 1 час. Refresh token живёт до 30 дней, хранится в виде хеша и меняется при использовании; повтор старого токена отзывает семейство. Изменение `AUTH_TOKEN_VERSION` в конфигурации отзывает все действующие подключения. OAuth-состояние хранится в приватном служебном префиксе Blob с consistent reads и ETag; кэшированное состояние не принимается.

Браузерная сессия владельца использует Secure, HttpOnly и SameSite cookie и CSRF-защиту. Данные пароля, токены, authorization code и полные подписанные URL не включаются в прикладные логи.

Vercel Deployment Protection не считается заменой авторизации MCP. Наличие корректного OAuth-входа и успешных вызовов из обоих целевых клиентов — отдельный критерий приёмки до работы с реальными материалами.

## 12. Ресурсы, безопасность рендера и ошибки

Сервер принимает JPEG, PNG и WebP. Фактический тип проверяется декодированием; изображение нормализуется, метаданные EXIF удаляются. Внешние SVG, HTML и файлы с несоответствием типа отклоняются.

Импорт по URL разрешён только через HTTPS. Запрещены localhost, приватные, link-local и служебные адреса; адрес назначения проверяется после DNS-разрешения и на каждом перенаправлении. Соединение выполняется с проверенным адресом, без повторного непроверенного DNS-разрешения. Действуют лимиты времени, размера и декодированных пикселей. Chromium не ходит за произвольными внешними ресурсами: все ресурсы заранее разрешены и доставлены сервером. Управление браузером, доступ к файловой системе и переменным окружения не выставляются MCP-инструментами.

Начальные эксплуатационные ограничения являются настройками продукта, а не лимитами тарифа:

| Параметр | Значение первой версии |
| --- | --- |
| Карточек в посте | 1–10 |
| Одновременных рендеров на проект | 1 |
| Новых попыток рендера в сутки | 100, изменяется владельцем через конфигурацию |
| Бюджет выполнения рендера | До 45 секунд |
| Максимальная длительность функции | 60 секунд |
| Срок блокировки попытки | 90 секунд с проверкой владельца при записи |
| Входной JSON инструмента | До 1 МБ до кодирования протокола |
| Base64-изображение | До 500 КБ декодированных данных, входит в лимит JSON |
| Импорт по URL | До 15 МБ, 25 мегапикселей, не более 3 перенаправлений |
| Размер дерева композиции | До 200 узлов и 12 уровней вложенности |
| Превью в ответе | До 512 КБ; весь MCP-ответ до 2 МБ |
| Итоговый PNG | До 15 МБ, передаётся через Blob signed URL |

Операции с большими файлами не проксируют их через тело ответа Vercel Function. Base64-вложения намеренно ограничены. Длительный результат не обещается после HTTP-ответа: отдельная очередь и workflow в первой версии отсутствуют.

| Код | Смысл и реакция |
| --- | --- |
| `AUTH_REQUIRED` / `FORBIDDEN` | Подключить или переавторизовать клиента; не повторять рендер до получения доступа |
| `INVALID_INPUT` | Исправить данные по схеме |
| `DESIGN_RULE_VIOLATION` | Исправить перечисленные компоненты или содержание |
| `ASSET_UNAVAILABLE` / `UNSUPPORTED_ASSET` | Выбрать доступное изображение поддерживаемого типа |
| `VERSION_MISMATCH` / `REVISION_CONFLICT` | Перечитать пакет или текущую карточку; не затирать чужую правку |
| `RENDER_BUSY` | Другой рендер активен; вернуть время допустимого повтора |
| `RENDER_TIMEOUT` | Попытка прервана; предыдущий результат сохранён |
| `IDEMPOTENCY_CONFLICT` | Использовать новый request_id для нового ввода |
| `RATE_LIMITED` / `BUDGET_EXCEEDED` | Прекратить автоматические повторы и сообщить владельцу |
| `STORAGE_UNAVAILABLE` | Результат не объявляется сохранённым; вернуть безопасное состояние повтора |

Клиентские инструкции разрешают не более двух автоматических исправлений после ошибок вёрстки. Бесконечный цикл рендеров запрещён. При изменении текста, меняющем смысл, агент согласует правку с владельцем.

## 13. Совместимость и переносимость

Приоритетные клиенты: ChatGPT и Claude, включая их мобильные приложения при доступности удалённых интеграций аккаунту. Подключение может первоначально потребовать веб-интерфейса клиента. Публикация в публичном каталоге не требуется для личного использования.

Официальные инструкции подключения фиксируются в README после проверки на реальных аккаунтах. Нельзя считать поддержку одним клиентом подтверждением поддержки вторым. Отдельно проверяются OAuth, чтение правил, вызовы рендера, изображение в ответе, скачивание PNG на телефон и восстановление сохранённого поста.

Если конкретный интерфейс не показывает image-блок, обязательным запасным результатом остаётся работающая ссылка на оригинальный PNG. Продукт не обещает автоматически прикрепить файл в формате, специфичном для определённого чата.

Логика бренда и компилятор не импортируют Vercel SDK. Сервер не вызывает LLM API: содержимое и композицию готовит выбранный пользователем клиент. Изменение хостинга требует замены адаптеров выполнения, авторизации и хранения, а не переписывания правил дизайна.

## 14. Стоимость и обслуживание

Для коммерческого использования планируется Vercel Pro. Hobby допустим для личного некоммерческого прототипа в пределах действующих условий. Небольшая нагрузка сама по себе не делает коммерческий сценарий разрешённым на Hobby.

Подтверждённые на дату документа ориентиры Hobby: 4 часа active CPU в месяц; Blob — 1 ГБ хранения и 10 ГБ передачи данных. Это внешние изменяемые условия, а не обещание цены продукта. Тариф, лимиты, доступность private Blob и совместимые версии SDK перепроверяются перед развёртыванием.

Стоимость зависит от браузерного CPU, выделенной памяти, операций Blob, размера оригиналов, числа повторов и скачиваний. До оценки числа постов выполняется серия из 20 типичных рендеров и фиксируются холодный/тёплый запуск, p50/p95 времени, CPU, размер PNG и операции хранения. До замеров число «бесплатных постов» не обещается.

Для каждого рендера записываются request_id, время, версия дизайна, результат проверок, размер выходных файлов и технический код ошибки. Временные метки хранятся в ISO 8601 UTC; суточный счётчик обнуляется по границе суток UTC. Владелец видит использование и расходы в Vercel Dashboard. Ограничения приложения и платформенные уведомления настраиваются до эксплуатации; приложение не обещает абсолютный денежный потолок только на основании счётчика запросов.

Готовые посты и версии хранятся до явного удаления владельцем средствами сопровождения. Автоматическое удаление рабочих материалов и MCP-инструмент массового удаления не входят в первую версию. Истёкшие OAuth-записи, операции и незавершённые временные объекты очищаются идемпотентной административной командой по срокам и ссылкам, без удаления используемых ресурсов.

## 15. Проверка и критерии приёмки

### Инфраструктура

- [ ] Приложение развёрнуто на Vercel без Supabase, внешнего браузера и LLM API.
- [ ] MCP обнаруживается и проходит OAuth из ChatGPT и Claude.
- [ ] Неавторизованные вызовы и попытки доступа к служебным префиксам отклоняются.
- [ ] Холодный запуск создаёт корректный PNG в пределах заданного бюджета; завершение освобождает браузер.
- [ ] Один входной набор в зафиксированном окружении даёт тот же макет; повтор на одном deployment имеет одинаковый хеш PNG.

### Дизайн и содержание

- [ ] В пакете бренда есть утверждённые правила, ресурсы и три шаблона.
- [ ] Пост по шаблону создаётся без изменения CSS.
- [ ] Новая разрешённая композиция создаётся, сохраняется как черновик и повторно используется по идентификатору.
- [ ] Чужие токены, неподдерживаемые компоненты, скрипты и произвольный CSS отклоняются.
- [ ] Длинный текст, отсутствие шрифта и неработающее изображение дают понятные ошибки вместо скрытого ухудшения результата.
- [ ] Визуальная проверка утверждённых эталонов подтверждает типографику, поля, логотип и обрезку фото.

### Надёжность и телефон

- [ ] Карусель из пяти карточек собирается последовательными вызовами, частичный результат доступен.
- [ ] Правка одной карточки сохраняет остальные и предыдущую версию.
- [ ] Повтор одного request_id не создаёт вторую успешную версию; другой ввод под ним отклоняется.
- [ ] Параллельные вызовы из двух клиентов не теряют правки; просроченная попытка не коммитит результат.
- [ ] После таймаута и повторного подключения к чату можно получить сохранённый результат и продолжить.
- [ ] При ошибке записи Blob сервер не сообщает об успешном сохранении.
- [ ] Оригинальный PNG скачивается из мобильных ChatGPT и Claude без изменения размера и повторного сжатия сервером.
- [ ] Просроченная ссылка не раскрывает файл; после get_post новая ссылка работает.
- [ ] Большой PNG доставляется напрямую из Blob, не превышая лимит ответа функции.
- [ ] Проверены отзыв токенов, повторное использование authorization code и refresh token.
- [ ] Импорт отклоняет внутренние адреса, небезопасные перенаправления и превышение лимитов.

Проверки включают тесты схем и правил, интеграционные проверки Blob/CAS и OAuth, реальные рендеры с длинным текстом и фотографиями, а также проверку на телефоне. Снимки сравниваются в одной зафиксированной среде; межплатформенное побитовое совпадение не является требованием.

Если актуальные клиентские возможности или библиотека авторизации не обеспечивают выбранную схему без дополнительных сервисов, это фиксируется как конкретный результат проверки совместимости. Дополнительный провайдер не добавляется скрыто: архитектура пересматривается с владельцем до эксплуатации.

## 17. Порядок перехода к реализации

1. Владелец проверяет эту спецификацию, прежде всего границы новых макетов, ограничения первой версии и работу с файлами из мобильного чата.
2. После одобрения составляется отдельный план реализации.
3. Первый проверочный срез доказывает связку OAuth → MCP → один эталонный рендер → приватный Blob → скачивание с телефона в обоих клиентах.
4. Затем добавляются дизайн-пакет, каталог, версии, черновики и восстановление.
5. Брендовая библиотека наполняется и принимается отдельно от технической готовности инфраструктуры.
